## 3. Candidate Notification and API Surfaces

### Primary candidate: `thread/tokenUsage/updated` (Server Notification)

The app-server pushes `thread/tokenUsage/updated` notifications during and upon completion of turns. The notification payload conforms to `ThreadTokenUsageUpdatedNotification`:

```typescript
type ThreadTokenUsageUpdatedNotification = {
  threadId: string;
  turnId: string;
  tokenUsage: ThreadTokenUsage;
};

type ThreadTokenUsage = {
  last: TokenUsageBreakdown;
  total: TokenUsageBreakdown;
  modelContextWindow: number | null;
};

type TokenUsageBreakdown = {
  inputTokens: number;
  cachedInputTokens: number;
  cacheWriteInputTokens: number;
  outputTokens: number;
  reasoningOutputTokens: number;
  totalTokens: number;
};
```

### Turn lifecycle correlation: `turn/completed` (Server Notification)

```typescript
type TurnCompletedNotification = {
  threadId: string;
  turn: Turn;
};

type Turn = {
  id: string; // UUIDv7
  status: "completed" | "interrupted" | "failed" | "inProgress";
  startedAt?: number | null; // Unix timestamp seconds
  completedAt?: number | null; // Unix timestamp seconds
  durationMs?: number | null;
  error?: TurnError | null;
  items: Array<ThreadItem>;
};
```

### Separate account credit query: `account/usage/read` (Client Request)

```typescript
type GetAccountTokenUsageParams = {
  threadId?: string | null;
};

type GetAccountTokenUsageResponse = {
  summary: AccountTokenUsageSummary;
  dailyUsageBuckets: Array<AccountTokenUsageDailyBucket> | null;
  threadUsage?: ThreadUsage | null;
};

type ThreadUsage = {
  threadId: string;
  estimatedUsageCreditsMicros: bigint;
  estimatedUsageUsdMicros: bigint | null;
  groups: Array<ThreadUsageBreakdownGroup>;
};
```

## 4. Exact Field Semantics

### `TokenUsageBreakdown` Fields

- **`inputTokens` (int64):** Cumulative prompt tokens presented to the model for the turn (in `last`) or whole thread (in `total`). In OpenAI token models, this includes both cached input and uncached input tokens.
- **`cachedInputTokens` (int64):** The subset of `inputTokens` that matched prompt cache prefixes and were read from cache without full re-computation.
- **`cacheWriteInputTokens` (int64, default 0):** Input tokens that caused new cache writes or checkpoints.
- **`outputTokens` (int64):** Total completion tokens generated by the model.
- **`reasoningOutputTokens` (int64):** The subset of `outputTokens` dedicated to internal reasoning / chain-of-thought tokens before producing visible assistant output.
- **`totalTokens` (int64):** Combined model processing token count. In native breakdowns, `totalTokens = inputTokens + outputTokens`.

### `ThreadTokenUsage` Fields

- **`last` (`TokenUsageBreakdown`):** Token breakdown strictly for the most recent turn.
- **`total` (`TokenUsageBreakdown`):** Cumulative token breakdown across all turns in the thread session so far.
- **`modelContextWindow` (int64 | null):** Maximum token capacity of the model's active context window (e.g. 258,000 or null if unspecified).

### Derived Field Formulas in CAE

- **`processedVolume`:** Defined as `totalTokens` if reported and non-negative; otherwise `inputTokens + outputTokens` when both are available; otherwise `null`. Never double-counts `cachedInputTokens` because `inputTokens` already subsumes cached input.
- **`cacheLeverage`:** Defined as `cachedInputTokens / inputTokens` when `inputTokens > 0`; otherwise `null`.
- **`reasoningFraction`:** Defined as `reasoningOutputTokens / outputTokens` when `outputTokens > 0`; otherwise `null`.

## 5. Capability and Version Uncertainties

1. **Protocol Schema Definition:** **PROVEN DETERMINISTIC.** Extracted directly from installed `codex-cli 0.153.2` via `codex app-server generate-json-schema --experimental` and `codex app-server generate-ts --experimental`. The notification `thread/tokenUsage/updated` with payload `ThreadTokenUsageUpdatedNotification` is an officially generated part of the Codex App Server Protocol v2.
2. **Local Session Log Format:** **PROVEN DETERMINISTIC.** Read-only inspection of historical local Codex rollout session files (`~/.codex/sessions/**/*.jsonl`) confirmed identical underlying token counters emitted in `token_usage_record` and `token_count` (`input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `total_tokens`, `model_context_window: 258400`).
3. **Live App-Server Notification Over Transport:**
   `LIVE_NOTIFICATION_SUPPORT: UNVERIFIED_UNTIL_NEXT_REAL_ASTRA_TURN`
   No model inference was run during this phase. Exact live arrival ordering relative to `turn/completed` will be passively observed on the next genuine Astra turn.
4. **Casing Conventions:** Protocol schema uses camelCase (`inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningOutputTokens`, `totalTokens`, `modelContextWindow`), while session rollout logs use snake_case (`input_tokens`, `cached_input_tokens`, etc.). The normalizer must accept both forms.
5. **Persistence across restart:** Schema indicates notifications are real-time events on the active transport.
6. **`cacheWriteInputTokens` presence:** The schema sets a default of 0, but older or alternative backend providers may omit it. Normalization treats missing `cacheWriteInputTokens` gracefully as `0` or `null`.

## 6. Privacy Implications

The native notification payload contains identifiers and context:
- `threadId`: Raw native UUIDv7 identifying the conversation thread.
- `turnId`: Raw native UUIDv7 identifying the specific turn.
- `items`: Present in `turn/completed`, containing user prompts, tool inputs/outputs, file diffs, and assistant responses.

### Strict Privacy Rules:
- **NO RAW IDS:** `threadId` and `turnId` MUST NOT be written to persistent storage (receipts, events.jsonl, measurements.jsonl). They may only exist transiently in volatile memory to correlate events, after which they are mapped to CAE's existing opaque SHA-256 HMAC/hashed session and turn keys (`sessionKey`, `turnKey`).
- **NO TRANSCRIPT / CODE / PROMPT:** Any fields containing prompt text, completions, tool invocations, or unified diffs MUST NEVER be captured or stored.
- **FAIL OPEN:** Any parser, validation, or persistence failure in token accounting must fail open silently without aborting or delaying the user's Codex turn.

## 7. Why Account Usage ≠ Token Usage

`account/usage/read` returns `GetAccountTokenUsageResponse` with:
- `estimatedUsageCreditsMicros`
- `estimatedUsageUsdMicros`
- `dailyUsageBuckets`

**Critical distinction:**
1. **Entitlement / Billing vs. Physical Computation:** `account/usage/read` reflects billing-tier calculations, estimated credits, and plan allowances (e.g. ChatGPT Plus 5-hour/weekly allowance percentages or API credit micros).
2. **Physical Token Breakdown:** `thread/tokenUsage/updated` reflects physical token counters (`inputTokens`, `outputTokens`, `reasoningOutputTokens`) processed by the neural model.
3. **Mislabeled Semantics Hazard:** Conflating credits or allowance points with token counters would mislead users into believing token volume directly translates into Plus 5-hour rate limit percentage. Plus rate limits are governed by multi-factor scheduling and sliding window buckets, not a fixed public token-to-point formula.
4. **Disposition:** `account/usage/read` is investigated in Phase 10 as an independent future signal and is completely isolated from token accounting.

## 8. Selected Implementation Path

1. **Normalization Layer (`src/token-usage.js`):**
   - Independent, zero-dependency pure function module.
   - Strictly parses, validates, and normalizes `ThreadTokenUsage` and `TokenUsageBreakdown` shapes.
   - Rejects non-numeric, negative, or malformed values; leaves missing fields as `null` (never guesses or zero-fills unknowns).
   - Calculates derived fields (`processedVolume`, `cacheLeverage`, `reasoningFraction`) using safe integer/float math.
2. **Transport Observer (`src/app-server.js`):**
   - Subscribe to `thread/tokenUsage/updated` notifications on the stdio transport during app-server sessions.
   - Maintain an in-memory correlation map from transient `threadId:turnId` to CAE's opaque `turnKey`.
   - Never persist raw `threadId` or `turnId`.
3. **Local Privacy-Safe Storage (`measurements.jsonl`):**
   - Write normalized turn measurement records to an isolated `measurements.jsonl` stream in the CAE state directory.
   - Preserve existing `events.jsonl` format and backward compatibility without destructive migrations.
